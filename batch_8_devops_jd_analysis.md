### 🎙️ High-Frequency Technical Interview Prep for Yokogawa

#### 1. Explain the architecture of a custom AWS VPC from scratch.
* **CIDR Block:** Define a private IPv4 block (e.g., `10.0.0.0/16`).
* **Subnets:** Segment into Public and Private subnets across multiple Availability Zones (e.g., `10.0.1.0/24` public AZ-a, `10.0.2.0/24` private AZ-a) for high availability.
* **Routing & Gateways:**
  * **Internet Gateway (IGW):** Attached to the VPC; public route table routes `0.0.0.0/0` to the IGW.
  * **NAT Gateway:** Deployed in a public subnet with an Elastic IP; private route table routes `0.0.0.0/0` to the NAT Gateway so private EC2 instances can download updates without being accessible from the internet.
* **Security Layers:** Security Groups (stateful, instance-level) and Network ACLs (stateless, subnet-level).

#### 2. What is the difference between an IAM User, IAM Role, and Instance Profile?
* **IAM User:** A permanent identity with long-term credentials (password or access key/secret key) representing a human or external legacy service. Best practice is to minimize or eliminate IAM user access keys.
* **IAM Role:** An identity with temporary security credentials (`sts:AssumeRole`) assumed by trusted entities (services, federated users, cross-account access) for a defined duration.
* **Instance Profile:** A container for an IAM Role that allows Amazon EC2 instances to automatically retrieve temporary credentials without embedding static keys on the virtual machine.

#### 3. How do you monitor an EC2 instance and set up automated recovery using CloudWatch?
* **Standard vs Detailed Monitoring:** Standard sends metrics every 5 minutes (CPU, Network, Disk I/O); Detailed monitoring sends metrics every 1 minute.
* **Memory & Disk Monitoring:** Since AWS hypervisors cannot see inside the OS, we install the **CloudWatch Unified Agent** on the Linux instance to stream OS-level memory utilization and disk space metrics.
* **Automated CloudWatch Alarm:** Create an alarm on `StatusCheckFailed_System`. If the underlying physical AWS host fails, the alarm action automatically triggers an **EC2 Auto-Recovery** action, migrating the instance to healthy hardware while preserving its private IP, Elastic IP, and EBS volume attachments.

#### 4. Give useful AWS CLI commands you use for troubleshooting.
```bash
# 1. Check running EC2 instances with public IPs and states
aws ec2 describe-instances --query 'Reservations[*].Instances[*].[InstanceId,State.Name,PublicIpAddress,PrivateIpAddress]' --output table

# 2. Check S3 bucket sizes and verify encryption status
aws s3api get-bucket-encryption --bucket my-enterprise-logs-bucket

# 3. Retrieve CloudWatch active alarms in ALARM state
aws cloudwatch describe-alarms --state-value ALARM --query 'MetricAlarms[*].[AlarmName,MetricName,Namespace]' --output table

# 4. Verify IAM role assumption and current identity
aws sts get-caller-identity
```

#### 1. How do you design an enterprise CI/CD pipeline with automated rollbacks?
* **Pipeline Stages:** Linting/Code Quality ➔ Unit Testing ➔ Security Scan (SAST/Trivy container scanning) ➔ Build & Push (Artifact registry / ECR) ➔ Deploy to Staging ➔ Integration Tests ➔ Production Deployment (Canary or Blue/Green).

  * **CloudWatch / Azure Monitor Metric Alarms:** If error rates (HTTP 5xx) surge beyond 1% post-deployment, webhook triggers the CI/CD pipeline or AWS CodeDeploy / ArgoCD to initiate instant rollback to the previous stable release commit.

#### 2. What are the key differences between AWS and Azure core networking architectures?
* **VPC vs VNet:** AWS uses Virtual Private Clouds (VPCs) divided into subnets mapped to specific Availability Zones; Azure uses Virtual Networks (VNets) with subnets that span across all Availability Zones within the region.
* **Security Controls:** AWS utilizes stateful Security Groups (at the ENI/instance level) and stateless Network ACLs (at the subnet level); Azure primarily relies on Network Security Groups (NSGs, stateful with priority rules) applied at both subnet and NIC levels.
* **Outbound Internet:** In AWS, private subnets require an explicit NAT Gateway in a public subnet; in Azure, default outbound access (historically automatic) now mandates Azure NAT Gateway or Azure Firewall for enterprise egress control.

#### 3. How do you troubleshoot a high-load or unresponsive Linux production host?
* **RHCSA Diagnostic Workflow:**
  1. **System Load & CPU:** Run `uptime` and `top` / `htop` to check 1, 5, and 15-minute load averages against CPU core counts.
  2. **Memory & OOM Killer:** Run `free -m` to inspect available RAM and swap. Check `dmesg -T | grep -i oom` to verify if the Linux kernel Out-Of-Memory killer terminated processes.
  3. **Disk I/O & Inodes:** Run `df -h` (space) and `df -i` (inode exhaustion). Use `iostat -xz 1 5` to identify I/O wait (`%iowait`) bottlenecks.
  4. **Network & Open Ports:** Run `ss -tulpn` to check listening sockets, and `ip a` / `ping` / `traceroute` / `curl -Iv` to isolate connectivity failures.
  5. **Service Logs:** Inspect `journalctl -u <service_name> -e -n 100` or `systemctl status <service_name>`.

#### 4. When would you choose Bash versus Python for DevOps automation?
* **Bash:** Ideal for native OS automation, systemd task wrappers, piping standard Unix tools (`awk`, `sed`, `grep`), file management, and lightweight container entrypoint scripts (`entrypoint.sh`).
* **Python:** Mandatory when interacting with Cloud APIs (AWS `boto3`, Azure SDK), complex JSON/YAML parsing, error handling across distributed services, database queries, and modular CLI utilities requiring unit test coverage.

#### 2. What is the difference between Docker `CMD` and `ENTRYPOINT`?
* **`ENTRYPOINT`:** Sets the default executable/command that always runs when the container starts. It is not easily overridden unless `--entrypoint` is explicitly passed.
* **`CMD`:** Provides default arguments to the `ENTRYPOINT`, or acts as the default command if no `ENTRYPOINT` is defined. Any command-line arguments passed to `docker run` will completely override `CMD`.
* **Best Practice:** Use `ENTRYPOINT ["python", "app.py"]` for microservices that act as dedicated binaries, and use `CMD` for passing default arguments that users might want to modify.

#### 3. How do you troubleshoot an EC2 or Linux instance when SSH connection fails (Connection Refused vs Connection Timed Out)?
* **"Connection Timed Out":** Indicates a **networking/firewall** issue before the packet reaches the OS.
  * Check AWS Security Group inbound rules (is port 22 allowed from your IP?).
  * Check Subnet Route Table (is `0.0.0.0/0` routed to an Internet Gateway?).
  * Check Network ACLs (NACL inbound and outbound ephemeral port rules).
* **"Connection Refused":** The packet reached the server, but the host rejected the connection.
  * The SSH daemon (`sshd`) is down or crashed (`systemctl status sshd`).
  * SSH is listening on a non-standard port instead of port 22 (`ss -tulpn | grep ssh`).
  * Local Linux firewall (`iptables` / `firewalld`) is rejecting the connection.

#### 4. How do you monitor cloud infrastructure and application health?
* **Infrastructure Metrics:** CPU utilization, memory pressure, disk I/O, and network ingress/egress tracked via AWS CloudWatch or Prometheus node-exporter.
* **Application Metrics (RED Method):** Request Rate, Error Rate (HTTP 4xx/5xx), and Request Duration (latency) visualized in Grafana dashboards.
* **Alerting:** Configured threshold alarms in CloudWatch/Alertmanager sending immediate webhook notifications to Slack or email when CPU > 85% for 5 consecutive minutes.

### 🎙️ High-Frequency Technical Interview Prep for Tekskills

#### 1. How do you design and secure an AWS VPC for a high-availability production application?
* **Subnet Segmentation:** Create a CIDR block (e.g. `10.0.0.0/16`) divided into public subnets (`10.0.1.0/24`, `10.0.2.0/24`) and private subnets (`10.0.10.0/24`, `10.0.20.0/24`) spanning at least two Availability Zones (AZ-a and AZ-b).
* **Traffic Routing:**
  * **Public Subnets:** Route `0.0.0.0/0` to an Internet Gateway (IGW) for public Application Load Balancers.
  * **Private Subnets:** Route `0.0.0.0/0` to a NAT Gateway deployed in the public subnet with an Elastic IP, enabling outbound internet access (for package updates and API calls) while blocking inbound internet traffic.
* **Security Boundaries:** Enforce stateful **Security Groups** allowing only necessary ingress ports (e.g., port 443 from ALB to EC2) and stateless **Network ACLs** as a secondary subnet-level perimeter.

#### 2. Walk through an incident troubleshooting workflow when an EC2 instance shows `StatusCheckFailed_Instance`.
* **Understanding Status Checks:**
  * `StatusCheckFailed_System`: Underlying physical AWS hardware host issue. Resolved by stopping and starting the instance (migrates to a healthy AWS host).
  * `StatusCheckFailed_Instance`: Internal OS-level failure (kernel panic, corrupted filesystem, out of memory, misconfigured network settings).
* **Troubleshooting Steps:**
  1. Retrieve EC2 System Log / System Screenshot via the AWS Console/CLI (`aws ec2 get-console-output`).
  2. If the OS failed to boot, create a snapshot of the root EBS volume, attach it as a secondary data disk to a recovery EC2 instance, inspect the logs (`/var/log/messages`, `/var/log/boot.log`), fix the corrupted config (e.g., `/etc/fstab` or network config), reattach, and restart.

#### 3. How do you monitor cloud resources and prevent operational downtime?
* **Proactive Metrics:** Monitor CPU utilization, memory pressure (via CloudWatch Unified Agent), disk space, and EBS volume queue depth.
* **Alerting Tiers:** Configure CloudWatch Alarms with dual thresholds:
  * *Warning Alert:* CPU > 75% for 10 minutes ➔ sends an automated Slack notification to investigate.
  * *Critical Alert:* CPU > 90% or `StatusCheckFailed` ➔ triggers high-priority SNS alert and initiates auto-scaling or automated EC2 instance recovery.

#### 4. What are IAM Best Practices for securing cloud access?
* Never use the AWS root account for routine tasks.
* Enforce **Least Privilege** access using customer-managed IAM policies.
* Require **Multi-Factor Authentication (MFA)** for all console users.
* Eliminate static IAM user access keys for applications by using **IAM Roles** and EC2 Instance Profiles with temporary STS credentials.
* Implement permission boundaries and condition keys (e.g., restricting access by source IP or requiring TLS).
