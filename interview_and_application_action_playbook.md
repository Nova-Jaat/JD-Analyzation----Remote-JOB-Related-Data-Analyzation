# Part 2: Technical Interview Masterclass & Scenario Q&A

---

### Scenario 1: AI-Assisted IaC & Guardrails
**Question:** *"How do you incorporate AI coding agents like Claude Code or Google Antigravity into your DevOps workflow without risking infrastructure outages, state corruption, or security leaks?"*

**Winning Answer:**
> *"I treat AI agents as high-speed scaffolding and linting accelerators, never as unmonitored executioners. My workflow uses a strict **4-stage human-in-the-loop guardrail framework**:
> 1. **Context Constraint:** When prompting an agent, I feed it existing module interfaces, variable schemas, and naming conventions so it cannot invent nonexistent resource types.
> 2. **Static & Security Verification:** Every AI-generated file must pass automated syntax validation (`terraform fmt -check`, `terraform validate`), followed by static security analysis using `tflint` and `tfsec`/`Checkov` to catch open ingress rules or unencrypted disks.
> 3. **Speculative Plan Review:** No AI-generated code is applied automatically. I inspect the `terraform plan` output specifically checking for unexpected resource destruction or recreation (`destroy and RE-CREATE replacement`).
> 4. **State Isolation:** All operations run against isolated remote backends with DynamoDB locking. This ensures AI accelerates our development velocity by 3x while our security posture remains 100% deterministic."*

### Scenario 2: Proving Backups & HIPAA Compliance (Zenara Health)
**Question:** *"How do you guarantee and prove that database backups restore, and how do you ensure an AKS cluster is HIPAA-ready from Day 1?"*

**Winning Answer:**
> *"A backup that hasn't been restored is simply a hypothesis. To guarantee backups restore:
> * I author an automated verification workflow: On a nightly schedule, an ephemeral container pulls the latest database snapshot from cloud storage, spins up an isolated database instance, restores the dump, and executes a synthetic query verifying record counts and schema integrity.
> * The script outputs execution time and status to Slack/monitoring; if the restore fails, it triggers an immediate P1 alert.
> 
> For **HIPAA readiness on AKS**:
> 1. **Data in Transit:** Enforce TLS 1.3 across all Ingress controllers and mutual TLS (mTLS) between internal microservices.
> 2. **Data at Rest:** Enable AES-256 customer-managed encryption on all Persistent Volumes and Blob storage accounts.
> 3. **Identity & Access:** Prohibit static cloud keys inside Kubernetes Secrets. Use **AKS Workload Identity** linking Kubernetes Service Accounts to Azure Managed Identities with least-privilege RBAC.
> 4. **Audit Trails:** Centralize all container logs and Kubernetes audit logs into Log Analytics with immutable retention policies for audit evidence."*

### Scenario 3: Kubernetes Workload Identity
**Question:** *"Explain how a container running inside AKS or EKS authenticates to cloud storage without storing static API credentials in secrets."*

**Winning Answer:**
> *"In AWS we use **IRSA (IAM Roles for Service Accounts)**; in Azure, we use **AKS Workload Identity**.
> 1. We establish OpenID Connect (OIDC) federation between the Kubernetes cluster's API server and the cloud identity provider (Entra ID or AWS IAM).
> 2. We annotate the Kubernetes Service Account (KSA) with the identity of the cloud role or Managed Identity.
> 3. When a Pod launches using that Service Account, the Kubernetes projected service account token volume mounts a short-lived, signed JWT token into the container.
> 4. When the application calls the cloud SDK, the SDK automatically sends this token to the cloud STS endpoint, which validates the signature against the cluster's OIDC discovery endpoint and returns temporary, short-lived cloud credentials (e.g., valid for 1 hour).
> 5. This completely eliminates hardcoded API keys and handles automatic credential rotation natively."*

### Scenario 4: The RHCSA Linux Troubleshooting Challenge
**Question:** *"A production server reports 100% disk utilization, but `du -sh /*` accounts for only 40GB on a 100GB volume. How do you troubleshoot and fix this without rebooting the server?"*

**Winning Answer (RHCSA Distinction):**
> *"This happens when files have been deleted from the filesystem namespace (`rm`), but active processes still hold open file descriptors to those files. The Linux kernel will not free the disk blocks until those file descriptors close.
> 1. **Identify the open handles:** I run `lsof +L1` (or `lsof | grep deleted`) to list all processes holding open unlinked file descriptors.
> 2. **Locate the file descriptor:** Once I identify the process ID (e.g., a logging daemon or database), I check `/proc/<PID>/fd/`.
> 3. **Remediate safely without downtime:** Rather than killing the production process, I truncate the file descriptor directly using:
>    `> /proc/<PID>/fd/<FD_NUMBER>`
>    This instantly zeroes the allocated disk blocks, reclaiming the disk space immediately without interrupting application availability.
> 4. Afterwards, I configure proper log rotation (`logrotate` with `copytruncate`) to prevent recurrence."*
