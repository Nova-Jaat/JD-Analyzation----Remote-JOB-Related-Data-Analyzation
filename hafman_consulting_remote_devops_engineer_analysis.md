## 🔬 6. High-Frequency Technical Interview Q&A Cheatsheet

### 🐧 A. Linux Administration & Troubleshooting (RHCSA Core)

#### Q1: "A production Linux server reports a Load Average of 25 on an 8-core CPU, but CPU utilization is only 15%. What is happening and how do you troubleshoot it?"
* **Answer:**  
  *"Linux Load Average measures both running/runnable processes (CPU-bound) and processes in **uninterruptible sleep state (D state)**, which are typically waiting on disk I/O or network file locks. If CPU utilization is low (15%), the bottleneck is disk I/O or waiting on hardware resources.  
  1. Run `vmstat 1 5` to inspect the `b` column (blocked processes) and `wa` (I/O wait percentage).  
  2. Run `iostat -xz 1` to identify which disk device has 100% `%util` or high `await` times.  
  3. Run `pidstat -d 1` or `iotop -o` to pinpoint the exact Process ID (PID) generating excessive read/write operations.  
  4. Inspect `dmesg -T` for disk controller or filesystem corruption errors, and `cat /proc/<PID>/stack` to see what syscall the blocked thread is waiting on."*

#### Q2: "A partition is reporting 100% full (`No space left on device`), but `du -sh` shows only 20GB used on a 100GB disk. How do you resolve this?"
* **Answer:**  
  *"This occurs under two primary conditions:  
  1. **Deleted Files Held Open by Active Processes:** A process (e.g., Nginx, Java, or an application log writer) deleted a large log file from disk, but the process still holds an open file descriptor. Run `lsof +L1` or `lsof | grep deleted` to find the process holding the inode, then restart the service or truncate the descriptor via `> /proc/<PID>/fd/<FD_NUM>`.  
  2. **Inode Exhaustion:** The disk has space in bytes, but ran out of file metadata nodes due to millions of micro-files (e.g., session tokens or cache files). Run `df -i` to verify inode consumption. If inodes are 100%, identify the folder using `find / -xdev -printf '%h\n' | sort | uniq -c | sort -k 1 -n` and purge the stale files using `find ... -delete`."*

### ☸️ B. Containers, Kubernetes & GitOps

#### Q3: "A Kubernetes Pod is stuck in `CrashLoopBackOff`. Walk me through your triage methodology."
* **Answer:**  
  *"I follow a systematic triage hierarchy:  
  1. `kubectl describe pod <pod-name> -n <namespace>`: Inspect the **Events** section and check `Last State: Terminated` with its exit code.  
     - Exit Code `137`: Pod was terminated by the OOMKilled killer (exceeded memory limit). I must increase `resources.limits.memory`.  
     - Exit Code `1`: Application runtime crash (uncaught exception, missing configuration/secret).  
     - Exit Code `127`: Entrypoint binary/command not found in the container image.  
  2. `kubectl logs <pod-name> -c <container> --previous`: Read the log stream immediately prior to the crash.  
  3. Validate ConfigMaps and Secrets referenced in `env` or `volumeMounts` exist and have correct keys.  
  4. Check Readiness/Liveness probes: If the probe endpoint returns 500 or takes longer than `timeoutSeconds`, Kubelet will repeatedly kill and restart the container."*

#### Q4: "How does Argo CD detect and handle GitOps configuration drift?"
* **Answer:**  
  *"Argo CD continuously compares the live state of Kubernetes cluster resources with the target declarative state defined in the Git repository.  
  - If someone manually edits a resource using `kubectl edit` or an ad-hoc command, Argo CD marks the application as **OutOfSync**.  
  - If **Self-Heal (Auto-Sync)** is enabled in the `Application` spec, Argo CD automatically applies the Git manifest back to the cluster, overwriting unauthorized manual changes.  
  - If an unmanaged resource is found in the cluster that was removed from Git, Argo CD's automated pruning (`Prune=true`) removes it, ensuring Git remains the single source of truth."*

### 🔄 C. CI/CD & Infrastructure as Code (Terraform)

#### Q5: "How do you manage Terraform state in a multi-developer, automated CI/CD pipeline?"
* **Answer:**  
  *"We never store state locally. In AWS, we configure a remote backend using an **Amazon S3 bucket with versioning and server-side encryption (KMS)**, paired with a **DynamoDB table for state locking (`LockID`)**.  
  - In Azure, we use an **Azure Blob Storage container with lease blob locking**.  
  - In CI/CD (GitHub Actions), we separate `terraform plan` and `terraform apply`. `terraform plan` runs on pull requests, posting a detailed diff comment on the PR. `terraform apply` only runs on merged code to `main`, executing within an isolated runner authenticated via OpenID Connect (OIDC) without long-lived static AWS/Azure credentials."*

### 📊 D. Monitoring, Logging & Observability

#### Q6: "How do Prometheus and Grafana monitor Kubernetes microservices, and how do you prevent alert fatigue?"
* **Answer:**  
  *"Prometheus uses a pull-based model, periodically scraping HTTP `/metrics` endpoints exposed by applications and exporters (such as `node-exporter` for OS metrics and `kube-state-metrics` for cluster state), discovered automatically via Kubernetes ServiceMonitors.  
  - In Grafana, we build dashboards utilizing PromQL queries to visualize golden signals: **Latency, Traffic, Errors, and Saturation**.  
  - To prevent alert fatigue, we configure Prometheus Alertmanager with:  
    1. **Symptom-based alerting** rather than cause-based alerting (e.g., alert on elevated 5xx error rate or SLO breach rather than transient 85% CPU spikes).  
    2. **Inhibition & Grouping rules** in Alertmanager to suppress downstream pod alerts when the host node itself goes down."*
